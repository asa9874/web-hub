# 장기 시간 진행 성능 진단 v1.1

2026-10-23. **진단 완료, 엔진 최적화 미수행, 성능 목표 미달.** 목표값은 `src/AcademySurvival/AGENTS.md`가 기준이다. 이번에는 기존 9일·30일 실행을 반복하지 않았다.

## 실측 범위

- Windows 10.0.26200 / Intel Core Ultra 7 258V / 논리 CPU 8 / Node v22.18.0. 브라우저는 headless Chromium, 1440×1000. 실제 사용자 PC·배포 환경을 모두 대표하지 않는다.
- NPC 100명, 시드 `performance-v1.1`, 학년·전공·성장 유형 혼합. AI·일과·이동·욕구/목표·관계·상호작용·효과·기억·세계 이벤트를 모두 활성화했다. 각 실행은 같은 시드의 새 세계이며 고정 인물/실제 저장은 수정하지 않았다.
- 시나리오당 **60분 구간**을 독립 프로세스에서 2회 측정했다. 별도 1회 CPU 프로파일은 평균/최대에서 제외했다. 아래 주간 명칭은 짧은 대표 구간이며 **실제 7일 측정이 아니다**.
- Node는 세계 초기화·최초 AI 연결·통계 조회·저장·화면 렌더링을 제외한 `world.advanceTime(60)`이다. 타임라인/API 호출 계측의 작은 오버헤드는 포함된다. UI는 동일한 100명 초기 스냅샷을 복원해 클릭부터 완료 후 다음 화면 프레임까지 2회 측정했다(자동화 클릭 비용 포함).
- 작업 중인 엔진 코드/기존 최적화 옵션의 기본값을 그대로 사용했다. 과거 장기 실행과 코드·초기 상태·계측 범위가 다르므로 과거 대비 성능 향상률로 해석하지 않는다. 엔진 번들 SHA-256과 상세 환경은 `performance-v1.1.json`에 보존한다.

- 각 실행에서 세계 시간60분·100명 AI·유효 위치·세계 이벤트 DAG 진단·기억 진단을 확인했다. 실제 발생한 상호작용/기억/관계 변화량을 기록했으며 그 밖의 경로가 모두 발생했다고 주장하지 않는다.

## 실측 병목과 코드 근거

| 우선순위 | 확인한 근거 | 해석·후속 방향 |
| --- | --- | --- |
| 1. 반복 깊은 복사 | 수업 CPU 프로파일에서 `structuredClone` 자체 약66%, 그중 `getCharacter` 호출 기원 약48%. 수업60분에 `getCharacter`44,947회, 위치 조회24,275회 | `systems/locationWorld.ts`의 방어적 복사 조회가 AI·조건·이동·효과에서 반복된다. 공용 getter의 격리 계약을 유지하며 한 판단/트랜잭션 안의 일관된 읽기 문맥을 재사용하는 것이 우선 |
| 2. 후보·경로·접근 조건 반복 | 수업에서 경로 요청6,088회. 타임라인의 AI 처리 약888ms, 세계 이벤트 약295ms(프로파일 실행의 포함 시간) | `systems/npcAi.ts` 후보/동기/지식 조회와 `locationRouting.ts`, `locationAccess.ts`, `worldEvents.ts` 참여자 조건에서 같은 정보를 다시 읽는다. 기존 후보 내부 경로 맵도 있어 중복 캐시를 새로 만들기 전에 유효 범위를 확대할 수 있는지 검토 |

| 4. 공통 이벤트 시점마다 순회 | `gameTime.ts`는 이미 예약 시각으로 점프하지만 모든 참가자의 `processAt`을 호출. 수업60분에 공통 처리39회, 교류64회. `motivationEngine.process`는 전체 상태 키, `npcAi.process`는 전체 AI 키를 순회 | 매분 강제 계산만이 문제는 아니다. 예약된/변경된 ID 집합과 상태 버전을 활용해 의미 없는 읽기를 줄여야 함. 분 단위 정밀도를 낮출 이유는 없음 |
| 5. UI의 게임 분당 프레임 대기 | `components/WorldEvents.tsx`는50명 이상이면1게임분마다 `requestAnimationFrame` 대기. 수업 브라우저 평균2.546초 대 엔진1.364초 | 두 값의 차이를 전부 렌더링 비용으로 단정할 수는 없다. 다만 현 방식은 계산이0이어도7일에10,080프레임 대기를 요구하므로 장기 목표에 부적합. 벽시계 기준 표시 주기와 실제 중요 경계에서만 갱신하는 별도 진행 조정이 필요 |

프로파일 비율은 샘플링 근사이며 inspector 오버헤드·GC가 포함된다. 타임라인 포함 시간은 내부 콜백의 다른 엔진 작업도 포함하므로 독점 비용처럼 합산하지 않는다. 이번 새 세계에서는 기억 정기 정리 자체가 주 병목으로 나타나지 않았다. 장기 기억·관계·이력 증가에 따른 비용은 별도 짧은 누적 상태 실험이 필요하다.

## 후속 설계와 허용 범위

**「실측 병목 기반 성능 최적화 v1」**

1. 위4개 고정 스냅샷/시드와 카운터를 기준선으로 보존한다. 대표 브라우저·워밍업·반복 수·기존 저장 나이를 추가해 응답 시간 분포를 측정한다.
2. 동일 판단/트랜잭션 안의 읽기 복사를 줄인다. 읽기 전용 투영·버전 키·무효화 경계를 명시하고 외부 호출자가 실제 상태를 수정할 수 없게 한다.
3. 경로 캐시는 출발지·이동 방식·능력/상태/권한·예상 통과 시각·출입 시간창·장소 버전을 포함한다. 닫힌 문을 과거 캐시로 통과시키지 않는다.
4. 효과의 전체 세계 백업을 변경 대상 중심의 원자적 롤백으로 바꾸는 방안을 검증한다. 효과 ID·관찰자 알림 순서·실패 원복·목표 증거를 보존한다.
5. 예약/dirty ID 처리와 활동 구간 적분을 검토한다. 일정·이동 도착·욕구 임계치·기간 효과·난수 평가 기회·정보 전달 등 모든 의미 있는 경계에서 구간을 나눈다. 단순 하루7회 반복이나 끝 시점의 활동을 전체7일에 적용하지 않는다.
6. UI/Worker는 응답성 대책으로 분리한다. 총 계산량 감소로 표시하지 않으며 사용자 선택이 필요한 경계에서 정확하게 정지하도록 진행 조정기를 설계한다.

**「NPC 시뮬레이션 LOD·지역 활성화 시스템 v1」**

- 원거리의 시각 표시·읽기 재사용·변화 없는 연속 상태의 경과 적분은 추상화 후보지만, 해당 NPC의 자율 목표·관계·정보·약속·중요 사건 참여를 꺼서는 안 된다.
- 우선 현재 결과와 동등한 최적화만 허용한다. 난수 기회·당시 위치/목격자·비밀·분기·원인 순서를 보존한다. 결과가 달라지는 시간 해상도/추상화는 차이·허용 범위·검증 근거를 별도 제시하기 전 적용하지 않는다.
- 원거리의 중요한 사건도 같은 인과 그래프와 실제 상태 변화 경로로 처리한다. 임의의 주간 결과/기억/관계를 사후 생성하지 않는다.

## 선택 중단·미검증

- `createGameClock.advanceTime`에는 현재 플레이어 선택 경계의 진행 중단/재개 프로토콜이 없고 세계 이벤트 v1의 플레이어 개입은 후속 범위다. 기존 별도 퀘스트 UI의 선택 기능까지 없다는 뜻은 아니다. 이번에 중요 선택을 자동으로 건너뛴 시나리오를 만들지 않았다.
- 후속 진행 조정기는 요청한 종료 시각보다 먼저 선택 이벤트에 도달하면 그 시점까지만 확정하고 정지해야 한다. 실제 진행 분·처리 사건 수·중단 이유를 기록하고 사용자의 선택 뒤 같은 RNG/예약 상태로 재개한다.
- 개입 없는7일 전체와 선택 중단 구간은 별도 성능 지표다. 이번에는 둘 다 미측정. 실제 시험/행사 주간, 긴 저장 이력, 브라우저4개 시나리오 전체, 수년 데이터 안정성도 미검증이다.
- 7일3초를 달성할 때까지 이번 진단을 반복하지 않는다. 게임 엔진·규칙·기억 보존 상한·RNG·저장 형식을 변경하지 않았다. 적용한 개선은 짧은 계측·시나리오 한정 재시도·프로파일 보존 등 **진단 작업 효율**이며 게임 성능 개선 수치가 아니다.

## 재현·검증 기록

- `node scripts/diagnose-academy-performance.mjs --minutes 60 --runs 2 --profile` (각 시나리오45초 프로세스 예산, 최대60게임분·최대3회로 제한).
- 최초 교류 준비는 잘못된 관계 ID로 실패했다. ID를 수정한 뒤 실제 상호작용0건인 준비 조건도 식별해, 해당 시나리오만 실제 요청20건 조건으로 다시 측정했다. 다른 통과 시나리오는 재실행하지 않았다.
- 실제 조립 코드의 이벤트→AI 재평가 콜백을 계측 조립에도 연결했다. 사건이 발생하는 시험/세계 이벤트 구간만 다시 측정해 표에 반영했다. 이 변경 전 수치와 현재 수치의 차이를 엔진 개선/퇴행으로 해석하지 않는다.
- `--scenarios social --resume`은 해시로 확인한 기존 엔진 번들을 재사용한다. 소스 변경 후에는 새 측정을 해야 한다. 원본 프로파일은 결과 폴더의 `*.cpuprofile`이다.
- 브라우저: 수업 초기 스냅샷을 `--sample classes --minutes 1 --output <probe.json> --save-initial test-results/academy-performance/browser-initial.json`으로 별도 내보낸 뒤, 로컬 Vite에서 `scripts/diagnose-academy-performance-browser.mjs`를 실행했다. 이1분 준비 실행을1시간 평균에 섞지 않았다.
- 원본: `test-results/academy-performance/report.json`, `browser-report.json`, 개별 샘플·프로파일·로그. 요약 증거는 [performance-v1.1.json](performance-v1.1.json)에 보존한다.
- 기존9일/30일·전체 게임 회귀·기존 게임 단위 테스트·생산 빌드는 재실행하지 않았다. 런타임 변경 없는 문서/진단 도구 작업으로 구문 검사·도구 실제 실행·범위 제한·결과 일관성·diff를 검증했다.
