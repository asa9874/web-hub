### 계측 해석의 한계

- 읽을 수 있었던 2026-10-22 로컬 rollout 파일 3개 중 2개에 usage가 있었다. 한 조각 6건, 다른 조각 5건이며 동일 수치가 token_count 이벤트에도 중복 기록된다. 둘을 합산하지 않았다.
- 조각별 마지막 thread 누적 input/cached/output은 각각 **627,030 / 515,328 / 639**, **444,564 / 274,048 / 586**이다. cached는 input의 일부다. 서로 다른 조각의 이력 중복 여부·전체 작업 범위가 불명하므로 합계를 전체 작업 사용량으로 제시하지 않는다.
- 해당 조각에 도구 호출 원문이 없어 파일별 읽기 횟수, 테스트/빌드 횟수, 동일 오류 재시도 수를 정확히 산출할 수 없다. 앞선 대화·검증 보고서의 정성적 근거와 구분했다. 인증 파일·다른 날짜 대화는 조사하지 않았다.
- 입력 토큰, 캐시된 입력, 출력, 실행 시간, 계정 한도는 동일 지표가 아니다. [OpenAI Prompt caching 문서](https://developers.openai.com/api/docs/guides/prompt-caching)는 캐시된 입력의 별도 계측을 설명하지만, 이를 이 계정의 과거 한도 소비나 청구액으로 환산할 근거는 없다. 실제 토큰 절감률·계정 사용량 감소율은 측정하지 않았다.

### 코드로 확인한 비용 구조와 미확인 병목

- 소유자/인물/장소/주제 인덱스가 존재한다. 매 판단마다 전체 NPC의 모든 기억을 검사하는 구조가 아니다.
- 정보 후보는 같은 장소의 정지 대상, 개인 기억 상위 후보로 제한한다. 전 세계 모든 NPC 쌍의 정보 공유 탐색은 확인되지 않았다.
- 새 기억마다 capOwner는 **개인 한도 부근(보통 129개)**에서 정렬한다. 전역 12,800개를 매번 정렬하는 것으로 해석하면 안 된다.
- 일일 유지보수/GC가 있으며 망각은 세계 시간에 따른 조회 계산을 사용한다. 같은 소유자·주장·출처 중복 저장을 제한한다.
- `actionEffects.ts`는 효과 트랜잭션마다 rollback용 `motivation.save()`와 원장 복사를 수행한다. `motivationEngine.ts`의 save는 상태 JSON 복제다. 많은 결과 이벤트에서 할당 비용이 커질 후보이나 실제 시간 비중은 미측정이다.
- `npcMemory.ts`의 통계는 전체 기억을 세 번 filter하며 view/clone을 생성한다. 일별 출력에 쓰이는 확인 가능한 불필요 할당 후보다. 소유자 후보 정렬·일일 GC도 프로파일링 후보다.
- 매분 통합 90MB를 디스크 자동 저장하는 경로는 확인되지 않았다. 마지막 배치 저장/clone과 효과 처리 중 메모리 내 직렬화는 구분한다.
- 결론: **통합 실행 비용은 측정되었지만 함수별 성능 병목은 확정되지 않았다.** 정상 엔진은 수정하지 않았다.

## F. 후속 검토 (이번 미적용)

- 실제 병목 측정이 필요하면 작은 고정 시나리오의 CPU/할당 프로파일부터 수집한다. 30일 재실행으로 시작하지 않는다.
- 효과 rollback의 변경 대상만 snapshot하기, 통계 계산에서 clone 제거, 소유자 후보 정렬 캐시 등은 프로파일 근거와 결정성·트랜잭션·저장 회귀 증거 후 별도 검토한다.
- 장기 실행 checkpoint/복원 재개는 실행 예약·원장·출처 계보를 보존하는 별도 설계가 필요하다. 이번 도구는 실패 시 이어 달리는 기능이나 자동 재시도를 제공하지 않는다.
- 현재 프리셋은 기억 작업용이다. 다른 시스템 프리셋은 실제 작업 수요가 생길 때 확장한다. 토큰/한도 비용의 완전한 계측과 도구 호출별 집계는 현재 기록만으로 불가능하다.
